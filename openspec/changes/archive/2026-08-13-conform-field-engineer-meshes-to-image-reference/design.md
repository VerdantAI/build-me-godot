## Context

The target character archetype is a field engineer: hardhat or helmet,
high-visibility vest or jacket, work boots, utility belt, clipboard/tablet,
radio, tools, and practical industrial materials. Existing rigged meshes remain
the source of animation compatibility. Image references and image-to-mesh
outputs are guides for silhouette, clothing volume, colors, accessories, and
texture intent.

The existing repository rules apply:

- packaged addon code stays under `addons/build_me_godot/`;
- artist manifests and outputs stay under `res://build_me_godot/`;
- external tools, model weights, Python packages, ComfyUI nodes, Blender
  extensions, Gator Model Studio, and animation assets are not installed
  automatically;
- code and model-weight licenses are reviewed independently;
- reconstructed meshes are immutable references and validation aids, not
  production topology;
- `neutral_a_pose_30deg_v1`, stable humanoid/socket names, and Godot
  `SkeletonProfileHumanoid` remain authoritative.

## Research Summary

Sources checked on 2026-08-13:

- [ComfyUI](https://github.com/Comfy-Org/ComfyUI): graph/node backend suitable
  for local pipeline orchestration; GPL-3.0 code remains external and is not
  redistributed.
- [ComfyUI-3D-Pack](https://github.com/MrForExample/ComfyUI-3D-Pack): broad
  experimental node suite for 3D inputs, meshes, UV textures, TripoSG, TRELLIS,
  and Hunyuan3D workflows. Treat as optional/user-managed because it pulls in a
  large Python and model surface.
- [TripoSR](https://github.com/VAST-AI-Research/TripoSR): MIT code and weights,
  single-image reconstruction, low VRAM for draft proxy meshes. Already listed
  in `LICENSES.md` as the safest baseline reconstruction adapter.
- [TripoSG](https://github.com/VAST-AI-Research/TripoSG): MIT repository,
  image-conditioned high-fidelity shape synthesis with at least 8 GB VRAM.
  Candidate successor provider after exact weight and transitive dependency
  review.
- [TRELLIS](https://github.com/microsoft/TRELLIS): MIT models and mostly MIT
  code, image-conditioned model recommended by the project, outputs mesh,
  radiance field, and Gaussian forms. Candidate provider after submodule and
  exact Hugging Face artifact review.
- [InstantMesh](https://github.com/TencentARC/InstantMesh): Apache-2.0
  repository and model card lineage, efficient sparse-view mesh generation;
  supports texture-map export but UV unwrapping can be slow at high extraction
  resolution. Candidate provider after exact weight review.
- [Wonder3D](https://github.com/xxlong0/Wonder3D): MIT repository, multiview RGB
  and normal generation with reconstruction. Useful best-practice notes:
  front-facing input, centered unobstructed subject, clear details after
  downsampling, and occlusion avoidance. Candidate reference technique, but
  dependency stack and older 256 px defaults make it less attractive as the
  first provider.
- [MV-Adapter](https://github.com/huanngzh/MV-Adapter): Apache-2.0 multiview
  adapter family with text/image, geometry, image-geometry, and ComfyUI paths.
  Best fit for future geometry-conditioned texture/reference refinement rather
  than direct production mesh output.
- [Stable Fast 3D](https://stability.ai/news-updates/introducing-stable-fast-3d):
  technically strong and fast, but released under Stability AI Community
  License with revenue-limited commercial use. Reject as a default dependency
  under this repo's permissive-only policy.
- [Hunyuan3D-2 license](https://huggingface.co/tencent/Hunyuan3D-2/blob/main/LICENSE):
  capable workflows exist in ComfyUI-3D-Pack, but the custom community license
  has territory limits and commercial/usage terms. Reject as a default
  dependency under this repo's current policy.

## Best-Practice Direction

### Input preparation

- Prefer the approved front/side/back field-engineer references generated by
  the Godot-owned ComfyUI workflow over a single arbitrary image.
- Normalize subject scale, crop, alpha/background, view labels, and pose before
  any reconstruction provider runs.
- Store all normalized inputs and provider outputs in the character folder with
  provenance. Do not modify or delete the approved reference run.
- Track field-engineer semantic targets explicitly: hardhat/helmet, hi-vis
  torso garment, work pants, boots, gloves, tool belt, radio, tablet/clipboard,
  safety glasses, logos/badges when present, and material/color swatches.

### Provider strategy

Use a layered pipeline rather than trusting one model:

1. Reference layer: approved ComfyUI images are canonical for style,
   materials, colors, props, and silhouette intent.
2. Proxy layer: TripoSR is the first supported reconstruction proxy because it
   is already reviewed and MIT. It produces a measurement/reference mesh only.
3. Candidate layer: TripoSG, TRELLIS, InstantMesh, Wonder3D, and MV-Adapter are
   recorded as optional providers with exact artifact/license review tasks
   before enablement.
4. Rejected default layer: Stable Fast 3D and Hunyuan3D remain manual
   experiments unless the project changes its dependency policy.

Promotion rule: once a candidate becomes a supported Build Me Godot option, it
must be represented in the installation environment app. A promoted provider
must define read-only checks, install-plan actions, explicit apply actions when
the action is allowed by project policy, license/provenance records,
destination paths, expected hashes when available, and verification checks. The
addon may still leave an action manual when automatic installation would be too
risky, but the install app must be able to explain and verify the required
state.

### Conformance logic

The conformance stage emits data, not production topology:

- align rigged meshes, reference planes, and proxy meshes in the
  `neutral_a_pose_30deg_v1` frame;
- measure front/side/back silhouette deltas against the primary and secondary
  meshes;
- identify clothing volume regions such as helmet, vest, belt, boot cuffs, and
  pockets as editable generated overlays or attachment candidates;
- extract palette/material targets for field-engineer surfaces;
- list secondary asset candidates with expected sockets such as `head`, `hand_l`,
  `hand_r`, `spine/chest`, `hips`, or existing project sockets;
- create duplicate-only Blender work files for sculpting/modeling experiments;
- validate that source meshes, source rigs, bone names, sockets, and humanoid
  profile compatibility are unchanged.

### ComfyUI/LoRA posture

LoRAs and adapters are allowed only as declared, optional, user-managed
artifacts. They must record:

- base model compatibility;
- artifact filename, source URL, exact license, and commercial-use status;
- expected ComfyUI node classes;
- VRAM class and known failure modes;
- whether the artifact affects images, multiview consistency, texture transfer,
  or mesh reconstruction;
- the fact that Build Me Godot will not download or install it automatically.

If a LoRA, adapter, custom node, or model weight is promoted from experiment to
supported workflow dependency, the install app must gain:

- a workflow declaration entry that names the required node classes and model
  artifacts;
- a `check` result that detects presence, version/hash when available, and
  license record;
- a read-only `plan` action with source, target, size, license, and risk notes;
- an explicit `apply` action only when the project has reviewed that mutation
  class, otherwise a manual action with exact verification criteria;
- a `verify` path that proves ComfyUI can see the node/model without queueing an
  expensive generation;
- tests proving addon enablement, `check`, and `plan` do not mutate external
  installations.

For field engineers, LoRAs should be treated as reference-image style/detail
controls, not as mesh topology controls. The first implementation should use
prompted safety-workwear targets and approved references before introducing a
domain LoRA.

the addon creates:

```text

  conformance_plan.json
  provider_inputs.json
  proxy_meshes/
  overlays/
  reports/
```

## UI and Agent Flow

1. User approves a field-engineer reference version.
2. User opens the conformance panel and reviews provider readiness.
3. User selects optional providers that are already locally installed and
   license-reviewed.
4. User starts `prepare conformance`.
5. The addon writes normalized provider inputs and a draft conformance plan.
6. Optional provider commands run only through explicit user action.
7. Blender handoff creates duplicate-only working files and overlays.
8. User reviews the conformance plan and approves selected edits/attachments.
9. Downstream Blender build applies approved guidance to generated work files,
   then validates rig/profile/socket stability before Godot import.

Agent commands should mirror existing character CLI behavior with stable JSON:

```text
inspect-conformance --character-id field_engineer --version v1
prepare-conformance --character-id field_engineer --version v1
approve-conformance --character-id field_engineer --version v1
```

## Risks / Trade-offs

- Image-to-mesh outputs may hallucinate hidden surfaces and collapse clothing
  layers. Mitigation: use them only as references and compare against approved
  multiview images.
- Field-engineer accessories can conflict with animation sockets or
  deformation. Mitigation: treat accessories as separate socketed assets first.
- Provider ecosystems move quickly. Mitigation: provider declarations include
  exact versions, hashes when available, and license records.
- Multiview and reconstruction tools may require large, fragile Python stacks.
  Mitigation: keep provider checks optional and user-managed.
- Good visual conformance can still produce bad gameplay readability.
  Mitigation: include artist review and in-engine validation screenshots before
  final registration.

## Open Questions

- Should the first conformance implementation run only TripoSR, or should it
  allow importing externally produced proxy meshes from TRELLIS/InstantMesh
  before those providers are automated?
- Should silhouette deltas be stored as raster overlays, mesh-space vertex
  regions, or both?
- Which socket taxonomy should represent field-engineer props when a consuming
  project has its own socket names?
- Do we need a separate `field_engineer_v1` semantic target schema, or can this
  live inside general character metadata?
